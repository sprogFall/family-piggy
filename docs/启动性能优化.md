# 启动性能优化

> 本文记录「长期未打开 App 后首屏等待过久」问题的成因诊断、优化方案、落地范围与验收方式。
> 相关背景与分层约定见 [`AGENTS.md`](../AGENTS.md)；模块细节见 [`项目手册.md`](./项目手册.md)。

---

## 1. 问题现象

Supabase 服务部署在境外，长期未打开 App 后冷启动，需要盯着开屏等待数秒才能看到数据。

先澄清一个常见误解：**不是每次打开都要重新登录**。登录态由 `persistSession: true` + `AsyncStorage`
长期保存在本机（`src/lib/supabase.ts`），冷启动走的是 access_token 的**静默续期**（`POST /auth/v1/token`），
只有 refresh_token 本身失效或会话被清理时才需要重新输入密码。

真正的问题在于：**首屏渲染被串行的网络往返（RTT）阻塞**，而且其中若干趟请求是重复或可合并的。

## 2. 现状诊断：首屏串行 6 个 RTT

以 `App.tsx` → `auth.store` → `ledger.store` → `BillsScreen` 的冷启动链路为例：

| 阶段 | 关键代码 | 串行 RTT | 说明 |
| --- | --- | --- | --- |
| ① 会话恢复 | `App.tsx` 以 `status === 'loading'` 作为开屏门；`auth.store.initialize()` → `authService.getSession()` | 1 | `getSession()` 会 `await initializePromise`，而 auth-js 的 `_recoverAndRefresh()` 在 access_token 过期（提前量 90s）时会真的发一次续期请求。长期未打开 ⇒ token 必然过期 ⇒ 这一趟一定会走 |
| ② 账本与家庭 | `ledger.store.load()` → `Promise.all([listLedgers(), listMyFamilies()])` | **4** | `listLedgers` 是 1 个请求；`listMyFamilies` 是 **4 个串行请求**：`auth.getUser()`（网络校验 JWT）→ `family_members` → `families` → `ledgers`。`Promise.all` 取最慢者，故本段耗时为 4 个 RTT |
| ③ 当月流水与分类 | `BillsScreen` / `HomeScreen` 的 `useFocusEffect` → `loadMonth()` + `loadCategories()` | 1 | 必须等 ② 产出 `activeLedgerId` 之后才能开始，因此与 ② 串行 |

合计约 6 个串行 RTT，再加上冷连接的 DNS + TLS 握手（约 2 个 RTT）与移动网络抖动。
境外单程 RTT 按 200–500ms 估算，3–10 秒的等待完全对得上现象。

诊断中另有两处浪费：

- **重复查询**：`listMyFamilies` 内的 `ledgers` 查询与 `listLedgers` 查的是同一批数据——RLS 已让
  `listLedgers` 同时返回个人账本与所在家庭账本（见 `src/services/ledger.service.ts` 注释）。
- **冗余鉴权请求**：`supabase.auth.getUser()` 是**网络请求**，而 store 手里早就有
  `session.user.id`，这次往返没有任何必要。

此外还有一个健壮性隐患：续期失败若是**网络类错误**，auth-js 会保留会话不登出，
此时 access_token 已过期，后续查询会被 RLS 以 401/42501 拒绝，表现为「加载账本失败」。

## 3. 优化方案（五档，按性价比排序）

### 第一档：请求瘦身 ✅ 已落地

把 ② 阶段的 4 个串行请求压成 1 个。

1. **删掉 `listMyFamilies` 里的 `auth.getUser()`**，改由调用方传入 `userId`（store 已有）。
2. **删掉 `listMyFamilies` 里重复的 `ledgers` 查询**，家庭账本 ID 由调用方用已加载的账本列表按
   `family_id` 本地关联（`familyService.listFamilies` 只返回家庭本身）。
3. **用 PostgREST 嵌入把 2 个请求并成 1 个**：
   `family_members?select=family_id,families(*)&user_id=eq.<id>`。

收益：② 阶段 4 RTT → 1 RTT，首屏串行 RTT 6 → 3。

### 第二档：本地快照 + 先渲染后刷新 ✅ 已落地

原实现除 `ledger:active:<userId>` 与设备级设置外，**没有任何业务数据落本地**，
冷启动必定白手等待网络。本档引入业务快照：

- 四个 store（`ledger` / `category` / `tag` / `transaction`）都新增
  `hydrate(userId)`：启动时先读本地快照并直接以 `ready` 状态渲染，随后由网络结果覆盖（stale-while-revalidate）。
- 快照 key 一律带 `userId`，沿用 `ledger:active:<userId>` 的记名方式，避免同设备多账号串数据。
- `App.tsx` 的启动流程改为「四个 store 并行 hydrate（纯本地，毫秒级）→ 再发起 `ledger.load()`」，
  顺序不可颠倒：若网络请求先返回、快照后写入，会用旧数据覆盖新数据。
- 账本列表一旦由快照就位，`BillsScreen` / `HomeScreen` 立刻拿到 `ledger` 并开始拉当月流水，
  于是 ②③ 两段从串行变为并行（第一档遗留的第 4 项由本档自然达成）。

收益：有快照时首屏等待趋近 0，网络只影响数据新鲜度；首次安装（无快照）仍走网络，
但已享受第一档的请求合并。

边界与注意点：

- **存储体积**：月份桶是唯一可能变大的数据，落盘时每个账本只保留最近 `3` 个月份桶（`monthKey` 为 `YYYY-MM`，
  可直接比较，纯函数见 `src/domain/snapshot.ts`），统计页的任意区间桶不落盘。
- **空桶不落盘**：没有任何流水的月份桶不写入快照——空桶渲染出来与「加载中」无法区分，
  刷新时反而会退回全屏加载态。
- **不用空结果覆盖缓存**：某个切片为空时整份不写（真正的清理只发生在 `reset()`），
  避免一次异常的空响应把可用缓存擦掉。
- **登出清缓存**：各 store 记录快照归属的 `ownerId`，`reset()` 时按该 id 删除对应 key，
  保证换账号或登出后不残留、不串数据。
- **隐私**：快照以明文存放在应用私有目录，与 session 同一信任级别（Android 应用沙箱内，不额外加密）。
- **失败保留旧数据**：网络刷新失败时仍保留快照内容，与既有「重拉失败保留本地快照」的策略一致。
- **已知取舍**：用户把某个月最后一笔流水删掉后，该月空桶不再落盘，上一次的非空快照会保留到被覆盖，
  下次冷启动可能先显示已删除的流水、随后被刷新结果纠正（SWR 的正常表现，无数据风险）。

### 第三档：把会话续期移出首屏关键路径 ⏳ 未落地

- 启动时先读本地 session 键（`sb-<project-ref>-auth-token`）判断「有登录态」即置 `signedIn` 渲染，
  把 `getSession()` 与续期放到后台，仅当续期明确失败（`invalid_grant` / 已撤销）才登出。
  注意「先注册会话监听、再读初始 session」的不变量不变。
- 补 `AppState` 监听：回前台 `supabase.auth.startAutoRefresh()`、进后台 `stopAutoRefresh()`
  （supabase-js 对 React Native 的官方建议，可缓解后台定时器被冻结导致的 token 过期）。
- 增加「拿到 401 强制刷新一次再重试」的重试逻辑，避免续期网络失败后所有查询被 RLS 拒绝。

收益：省 1 个 RTT，并修掉后台恢复时的会话状态隐患。

### 第四档：网络层治本 ⏳ 未落地（需要账号/运维决策）

- Supabase 项目 region 选择东京或新加坡。
- 自建反向代理 + 自定义域名（Cloudflare Worker 反代 REST/Auth，App 侧用自定义域名替换
  `EXPO_PUBLIC_SUPABASE_URL`）。注意 **Realtime 的 WebSocket 不能这样代理**，需单独直连原域或改用拉取刷新。
  也可使用 Supabase 官方 Custom Domain（Pro 计划），少一层自维护。
- 不要采用「加速 IP + hosts」类方案：IP 会漂移且会破坏证书校验。

### 第五档：其他小项 ⏳ 未落地

- 各 service 的 `select('*')` 改为明确字段（`ledger` / `profile` / `transaction` / `category`）。
- 启动时 `profileService.getProfile` 可先用缓存渲染、后台刷新。
- 终极方案：一个 Postgres RPC `bootstrap(p_ledger_id, p_start, p_end)` 一次返回
  profile + ledgers + families + 当月流水 + 分类，一次 RTT 拿到首屏全部数据。

| 场景 | 优化前 | 优化后 |

## 5. 验收方式

- 自动化门禁：`npm run typecheck` 与 `npm test -- --ci` 全绿（本次变更后 76 个测试套件 / 538 个用例通过）。
  新增 / 修改逻辑均已补测试：
  - `family.service.test.ts`：单次嵌入查询与参数（`select('families(*)')`、按 `userId` 过滤）、
    RLS 过滤为 null 的行、失败文案；
  - `domain/snapshot.test.ts`：裁剪规则（按账本分组、跨年、边界值）；
  - `ledger.store.test.ts`：家庭账本 ID 本地关联、失败不覆盖快照、hydrate 恢复上次账本、
    无快照保持加载态、跨账号隔离、读取期间切换账号丢弃过期快照、reset 清缓存；
  - `category/tag.store.test.ts`：load 落盘 / hydrate 读回 / 账号隔离 / reset 清缓存；
  - `transaction.store.test.ts`：月份桶裁剪到最近 3 个月、空桶不落盘、hydrate 直接渲染、
    Realtime 写入后快照同步、账号隔离、reset 清缓存。
- 手工验证（Android 真机）：
  1. 登录并打开账单页 → 完全杀掉进程 → 重新打开：应**立即**看到上次的账本与当月流水，
     随后后台刷新（下拉刷新指示或数据静默更新）。
  2. 断网冷启动：应仍能看到上次快照数据（而不是整屏「加载失败」）。
  3. 登出后重新登录另一账号：不应看到上一个账号的任何账本与流水。
- 请求数验证：客户端日志或 Supabase 日志中，冷启动的 REST 请求数应明显下降
  （家庭相关由 4 个串行请求降为 1 个）。

## 6. 风险与回滚

- 快照与远端不一致：以网络刷新结果为准覆盖，且失败时保留快照；用户可下拉刷新强制重拉。
- 存储占用：月份桶裁剪到最近 3 个月，分类/标签/账本数据量天然有界。
- 回滚：删除各 store 的 `hydrate` 调用与 `App.tsx` 的启动编排即可回到纯网络路径，
  快照读写是独立模块，不影响数据正确性。
